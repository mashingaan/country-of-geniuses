# Community model

The project has two equal contribution paths.

## Build the commons

Developers can add skills, schemas, source adapters, MCP contracts, tests, translations, and maintenance notes.

## Do the local work

Participants can verify a service boundary, check a public signal, test a language-specific procedure, review a draft, or confirm an outcome in their community.

Local knowledge does not need to be packaged as code to be valuable. A clear source note or correction can prevent a whole class of routing errors.

## Bring an honest signal

The community is deliberately open to local participants, researchers, developers, and people who simply noticed a public-service problem. Send a concrete signal through the [Civic signal issue form](https://github.com/mashingaan/country-of-geniuses/issues/new?template=signal.yml) or propose a redacted change by pull request.

Useful signals explain what happened, the general jurisdiction and location, when it was observed, the public evidence, whether an existing request is known, and what outcome would count as useful. Honest uncertainty is better than a confident guess.

The review process turns useful signals into a growing public knowledge base: verified problem cards, local skills, jurisdiction packs, source notes, and integration guidance. A raw signal is a lead, not a fact. Contributors should preserve that distinction.

Do not include names, direct contact details, exact private addresses, credentials, private correspondence, identifying media, or emergency situations. Use the emergency or public-service channel directly when immediate action is needed.

## Maintainer responsibility

Maintainers should prefer evidence over volume, preserve uncertainty, reject unsafe automation, and make stale integrations visible. The project measures learning and useful outcomes, not complaint counts.
