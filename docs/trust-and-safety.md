# Trust and safety

The project earns trust through inspectable process and honest limits. Open source is an opportunity for review, not proof that every contribution is safe.

## Evidence and uncertainty

Every claim about a public problem should be tied to a source, the correct kind of timestamp, access time, and a short explanation of what the source supports. Distinguish when a problem was observed from when a reporting service created or updated its record. Mark stale, conflicting, incomplete, and unverified evidence. Never turn a weak signal into an accusation.

## Public and private boundary

Public repository content may contain public URLs, general locations, service names, redacted summaries, and reproducible process notes. Keep the following in a participant-controlled private store:

- Names and direct contact details
- Exact private addresses
- Photos, recordings, or documents that identify people
- Credentials, tokens, cookies, and private API responses
- Unpublished correspondence and case references

An exact public facility address may be appropriate only when it is already public, necessary for routing, and does not identify a private person or home.

## Human confirmation

The default is prepare, show, and wait. Before an external action, the participant must be able to see:

- The recipient and channel
- The exact message or structured fields
- The evidence supporting the request
- Data that will leave the local environment
- Possible duplicates, risks, and irreversible effects

The first releases do not support autonomous external submission. Any future exception needs a narrow allowlist, rate limit, duplicate check, audit trail, and an explicit opt-in.

## Duplicate and abuse prevention

One problem should result in one coordinated request where possible. Before submission, compare the candidate with existing public requests and the participant's private history. Use idempotency keys or an equivalent local record when a connector supports them. Never optimize for the number of messages sent.

## High-risk situations

Do not use this project as an emergency dispatcher. Escalate urgent danger to the appropriate local emergency channel. Pause for human review when a case involves medical care, legal rights, law enforcement, elections, immigration, vulnerable people, threats, suspected crime, or claims about an identifiable person.

## Outcomes

Record the distinction between prepared, submitted, acknowledged, resolved, and verified by a person. A status change in a government system is evidence about that system, not proof that the real-world condition changed.

## Fraud and anomaly analysis

Anomaly signals can support review. They are not findings of fraud. Any future analysis must show the source data, calculation, missing-data limits, alternative explanations, and human review path.
